# 概念字典

## 数据端口

keywords: 端口, 数据流, 数据来源, 温度从哪, 如何传入, 没有真实数据, 属性如何进入, 读数, 传感

设备读数不会顺着控制连线走。控制连线只决定谁被激活；要把温度之类的值交给后续节点，必须通过数据端口：在产生该值的设备节点用 OUT 数据端口输出，在需要使用该值的节点用 IN 数据端口接收，再用数据连线把两端连上。仅在接收节点声明一个变量名是不够的，必须有数据连线才能把值传进来。

## 变量与属性

keywords: 内部变量, 属性名, 属性映射, 设备属性, 不是变量, condition.object, 判断温度, temp

设备属性名不是节点变量名。设备属性要先在设备节点（`DEV_NODE`）中通过 `attributesMapping` 映射为该节点的节点变量，再经数据端口传给下游。下游节点的触发器条件中，`condition.object` 只能引用本节点已声明的节点变量名，不能写设备属性名，也不能写其他节点的变量名。

## 控制流

keywords: 控制连线, 谁激活谁, 接口连线, 执行流, NODE_TO_NODE

控制连线是执行令牌：上游完成后，下游才开始。控制连线不携带温度、时间或其它测量值。需要互斥分支时用分支节点（`BRANCH`）的多个出口；多路汇合时用聚合节点（`AGGREGATE`），汇聚门槛等于实际会到达的控制入边数。互斥分支汇合时汇聚门槛为 1，因为同一时刻只有一路到达。

## 能力参数

keywords: 没有目标温度, 无法指定, 参数不够, 散热只有, 能力没有, 发明参数

设备能力有哪些能力参数，就只能填哪些。目录里散热只有时间参数，就不能再造一个目标温度参数。用户口头多出来的数字，能对应到已有能力参数就填进去，对不上就写进 `metadata.description`，不要为了看起来完整而编造字段。

## 含糊描述

keywords: 请确认, 请补充, 需要确认, 向你确认, 先不保存, 歧义, 请明确, 等你确认, 我理解可能

生成过程没有人在线回答。含糊句按最合理解读继续编写工作流草稿，把解读写进 `metadata.description`。不要停下来等人，也不要因为不确定就拒绝保存；编写、校验、无 blocking 后保存草稿，留给人在设计器里修改。

## 系统标识

keywords: aggregateCount, nodeLifecycleState, signalName, 不需要声明, 从哪来, 没有声明, 未声明

`nodeLifecycleState`、`signalName`、`aggregateCount` 是引擎内置的系统标识，不在节点变量（`internalVariables`）中声明。`nodeLifecycleState` 表示本节点的生命周期状态；`signalName` 表示 IN 控制接口收到的信号名；`aggregateCount` 是聚合节点的已到达入边计数，引擎自动初始化为 0。这三个标识可直接用于触发器的 `condition.object` 和 UPDATE 动作的 `targetName`。
