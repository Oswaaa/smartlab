§2 相关工作
03 / 22

缺的不是自动化，是任务级模型

现有路径分别解决设备调用、过程编排与资产描述。没有一条把能力、运行状态、数据依赖与执行边界，组织进同一次任务表示。

脚本与设备接口

对集成和发令有效。设备状态、数据传播、约束处理往往散落在脚本、适配与控制代码里，而不是任务级模型。

常规工作流编排

能说清步骤如何组织、执行如何推进。节点仍被当作动作或服务，并不携带设备状态、数据依赖与约束语义。

资产级系统模型

能描述实验室资源与行为关系。通常不说明：如何按任务选出能力，并把状态、数据、信号、约束组装成一次可执行表示。

剩余缺口：一个任务级模型，使能力、状态、数据依赖与执行约束成为同一切片里的协调元素。

设计思路

严格按论文三条线，不攻击具体系统。缺口咬在“任务级模型缺失”，不要滑向“我们功能更多”。为下一页主张铺路。

内容框架

  1. 脚本：集成有效，语义碎在代码里
  2. 工作流：会推进，节点仍是动作
  3. 孪生/MBSE：会描述资产，不会按任务组装执行

核心主张F1 · F2

两个定义，撑起整篇方法

实验任务执行不是顺序调用设备命令，而是实验室系统在特定任务上下文中的整体动态演化。

F1 · EXECUTION SLICE

工作流是实验室系统的任务切片

它不是外挂在设备之上的流程图，而是从实验室整体中切出本次任务所需的能力、关系与边界，形成可执行的系统表示。

后面所谓创建任务，就是切出这一片，并落到具体设备上。

F2 · CAPABILITY MAPPING

节点是设备能力的过程层映射

节点不是命令包装器。它带着明确的状态、数据与信号语义，引用设备对象上的一项能力，而不是在流程里重写该能力。

设计思路

§3.1 系统抽象
05 / 22

实验室被写成一个四元组

L = ⟨ R, F, C, Π ⟩　资源提供可执行对象，工作流按任务组织它们，约束看守边界，协议是三层共用的语言——不是第四台执行引擎。

R 静态资源

设备资产及其连接。每个设备是可执行对象：能力定义 + 状态机。

F 动态工作流

任务切片。组织被选中的能力，以及它们的时间、控制与数据关系。

C 约束

实验室范围的基线，与仅在本任务期间生效的边界。监护而不是编排。

Π 协议

信号格式与交互约定。让三层协调，而不去改对方的内部状态。

随后四页按 R → F → C → Π 逐层多引进一个词。工程部分将按同一顺序回收。

§3.2 资源层F3
06 / 22

能力描述能做什么，状态机描述正在发生什么

设备对象 D = ⟨ CapD, SMD ⟩。能力模型是静态语义基，不主动执行；属性可直接观测，不必绕过状态机。

Cap　能力模型

⟨ Attr, Ops, Adpt, Port, ConstrD ⟩

  • 属性空间：连续或离散的可观测量
  • 操作能力：对外暴露的可执行操作
  • 适配契约：命令模板、事件与反馈的登记
  • 端口：属性级数据端点
  • 内置约束：与任务无关的本地边界
分离

SM　状态机

执行交互与状态转移的行为中枢

  • 接收控制信号后发生转移
  • 向适配器发出操作，再接收反馈
  • 对外公布设备状态
  • 按内置约束监视属性，越限进入异常

为什么状态机还要再分成两个空间？下一页回答。

§3.2 状态机F5 设备侧
07 / 22

指令进度不是物理工况

状态空间写成 St = Stcmd × Stop。接口只作端点，不藏逻辑。转移由「当前状态 + 入口 + 信号」共同决定。

两个空间

  • 指令空间：这条操作命令走到哪了——待发、已派发、执行中、完成或失败。
  • 运行空间：装置现在处于什么工况——空闲、加热、保持，或异常。

一台装置可以“指令已完成”而“工况仍在保持”；也可以“指令失败”而“工况已入异常”。二者必须分开写。

接口是边界，不是程序

收控制命令 收适配器事件 向适配器下发 对外公布状态

工作流、人工干预、约束处置，都可以从不同入口走进同一台状态机。工作流并不直接拧硬件。

内置约束越限时，状态机就地进入异常——这是后面“两级约束”的本地一侧。

设计思路

讲清双空间。接口端点原则为“多入口进同一台状态机”埋伏笔。不讲急停插队等工程调度。

内容框架

  1. CMD vs OP
  2. 接口四类端点
  3. 转移规则的要素
  4. 内置约束就地生效

§3.3 工作流层F1 · F2
08 / 22

节点引用能力，不重写能力

执行节点的映射 Map = ⟨ D, op ⟩。功能节点承担分支、同步、等待。节点生命周期是过程态：受设备回传影响，但与状态机状态不等价。

切片里有什么

被选中的能力，以及它们之间的时间、控制与数据关系。工作流描述的是实验室在该任务中如何演化，而不只是步骤清单。

执行节点

指向某个设备对象上的一项操作。参数、属性与信号语义来自该对象，而不是在节点里另写一套。

节点自己还带什么

内部变量、过程生命周期、允许的转移、接口、端口、以及可被触发器调用的动作。

如果节点只是发一条命令，第 4 页的主张就塌了。关键是节点带着状态、数据与信号语义去映射能力。

§3.3 拓扑与触发F4 · F5
09 / 22

信号决定何时走，数据决定带上什么

F = ⟨ VF, EI, EP ⟩。接口边包含节点之间，以及节点与设备状态机之间的信号路由。端口边是持续的数据依赖。

实线　接口连接 EI

控制与通知：激活下游、向状态机发出启动或中止、收回设备状态。

信号到达接口后，绑定的触发器检查条件；成立则执行动作——更新变量、请求生命周期变化、或再发出信号。

虚线　端口连接 EP

数据依赖：温度、设定值、中间量在连接有效期内保持可取用。

数据通道不负责“下一步该不该发生”。它只保证该在的值能被下游看见。

节点完成 ≠ 设备指令完成；前者常常以后者为条件。两套生命周期要分开写——系统后文会保持这张图，而不是拧成一根线。

设计思路

F4 在此成形。触发语义用一条因果链即可，不讲轮询。F5 对照句放在底栏，便于第 16–17 页回收。

内容框架

  1. EI 何时推进
  2. EP 数据如何到达
  3. 触发器 ⟨条件, 动作⟩
  4. 两套生命周期

§3.4 约束层F6
10 / 22

本地先停住，全局再看见并处置

C = ⟨ BC, Obs, VH, TC ⟩，观测 Obs = ObsR ∪ ObsF。内置约束与约束层互补，不是重复建设。

设备内置 ConstrD

与任务无关，由状态机就地监视属性。越限立即进入异常。例如装置自身上限 500℃。

基线 BC　始终在

看守实验室会话，不论当前有没有任务。例如运行状态不得停留在异常而不被理会。

任务包 TCτ　随任务出现

本任务目标与本任务边界。例如加热任务要求温度不超过 120℃，否则停止。

约束层只通过可观测空间看世界：设备属性与状态，以及节点、任务的过程态。处置包括警告、停止、中止等——它监护编排，并不取代编排。

§3.1 协议 ΠF7
11 / 22

协议约定怎么说，并不代替谁来做

Π 定义信号外形与交互约定，被资源、工作流、约束共用。适配器登记命令模板与事件；能力模型提供统一语义视图。

共同语言

  • 启动、中止、状态公布、遥测与事件，需要可识别的外形

§4.1 案例
12 / 22

反应釜加热：三层装进同一切片

这是结构可实例化的说明，不是性能评测。一个对象模型、一个加热节点、两级约束。

约束

基线：运行状态不应无人理会地停留在异常。任务：温度 ≤ 120℃，否则停止。观测：温度、设备状态、加热节点生命周期。

工作流切片

加热节点映射 ⟨反应釜, 加热⟩。上游完成信号激活本节点；本节点完成后再激活下游。温度进入节点变量，并经数据端口传给后续步骤。

资源对象 + 适配器 + 物理装置

属性含温度；能力含加热；适配契约登记加热命令。内置上限 500℃——装置自己的底线，比任务边界更宽，也更硬。
