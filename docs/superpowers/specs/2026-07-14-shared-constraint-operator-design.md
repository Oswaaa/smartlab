# 共享约束操作符设计

## 目标

统一设备能力模型、工作流模型和约束模型使用的比较操作符，同时保持三个模型彼此独立。此次改造不兼容 `GT`、`LE`、`EQ` 等旧值。

## 契约归属

`ConstraintOperator` 是多个独立模块交换和持久化时共同使用的语义词汇，因此定义在 `protocol-dict.json`：

```json
{
  "type": "string",
  "enum": [">", "<", ">=", "<=", "=", "!=", "BETWEEN", "IN"]
}
```

`constraint-model.json`、`device-capability-model.json` 和 `workflow-model.json` 只引用该共享定义，不互相引用。

模型专属枚举仍留在各自模型内。是否被多个独立模型共同交换，是进入 protocol 的判断依据；单纯属于某个模型的实现细节不会进入 protocol。

## 操作数语义

- `>`、`<`、`>=`、`<=`、`=`、`!=`：右操作数是单值。
- `BETWEEN`：右操作数是恰好包含两个元素的数组，按 `[下界, 上界]` 表示闭区间，并要求下界不大于上界。
- `IN`：右操作数是至少包含一个元素的数组，表示允许值集合。

各模型根据自身业务收窄共享操作符：

- 约束规则和工作流条件可使用完整集合，并在本模型中校验右操作数形状。
- 设备能力模型的 `intrinsicConstraints.boundaryValue` 当前是单个数值，因此只允许六个单值比较操作符，不开放 `BETWEEN` 和 `IN`。将来若要支持区间，应先显式扩展该模型的数据结构。

## 代码行为

- 后端只接受上述八个标准值，不转换旧别名。
- 前端选项、默认值、标签和提交值全部使用标准值。
- 删除所有 `GT/LT/GE/GTE/LE/LTE/EQ/NE/NEQ/NOT_IN` 兼容映射。
- 遇到非标准操作符时由后端校验拒绝，不能静默转换成默认值。
- `BETWEEN` 和 `IN` 的数组在字符串存储边界上使用 JSON 数组文本，读取后按 JSON 数组校验。

## 验证

- Schema 引用测试：三个模型均能解析 protocol 中的 `ConstraintOperator`，且不存在模型间反向引用。
- 服务测试：八个标准值可用；旧别名被拒绝；`BETWEEN` 和 `IN` 的错误操作数被拒绝。
- 残留扫描：生产代码和前端中不存在旧操作符值或兼容映射。
- 回归验证：运行后端完整测试与前端生产构建。
