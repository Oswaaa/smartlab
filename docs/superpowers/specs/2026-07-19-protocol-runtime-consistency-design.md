# Protocol 与运行时一致性改造设计

## 目标

把当前系统从“部分读取 protocol/schema、部分重复硬编码、部分旧接口绕过校验”收敛为单一规范源与显式执行语义并存的架构，同时修复工作流聚合节点的执行错误。

## 规范边界

- `protocol-dict.json` 定义跨模块通信格式、Topic 约定、共享数据类型和共享信号格式。
- 各模型 JSON Schema 定义各自模型的结构、枚举、必填项和模型内约束。
- 前端展示枚举和可配置项从后端 schema metadata 获取，不维护第二套业务枚举。
- 后端通过正式 JSON Schema 验证器校验消息和模型，不用不完整的手写 schema 解释器冒充完整校验。
- 工作流和状态机的推进、动作执行、事务和错误处理由 Java 显式实现。执行层可以使用 `switch` 或执行器注册表，但支持范围必须与 schema 完全一致。

## 工作流执行

聚合节点采用一次聚合执行一个 `TASK_STEP` 的语义。到达聚合节点的各前序分支写入同一个聚合步骤的到达状态；`ALL` 聚合只有在本次流程实例中全部预期前序完成后才继续，且后继只路由一次。失败、取消和子流程中的聚合遵循同一实例边界。

工作流定义保存时先执行完整 schema 校验，再执行语义编译。节点类型、功能类型和控制信号的允许集合来自 schema metadata；引擎仍以代码实现 `START`、`END`、`BRANCH`、`AGGREGATE` 的确定语义。

## 动作执行

状态机和工作流动作使用执行器注册表。schema 中可选的动作必须存在执行器，否则应用启动或定义保存时失败。运行时遇到未知动作应终止当前执行并记录明确错误，不允许只打印警告后继续。

当前没有业务实现依据的 `ASSIGN`、`UPDATE_VARIABLE`、`EXECUTE_LOGIC` 不作为可用协议能力暴露；已有设计器生成的无效动作同步清理。需要变量更新时应在未来以独立、经过定义和测试的动作重新加入。

## Adapter 与 MQTT

- 当前可执行配置格式限定为 `INI`、`JSON`，通信协议限定为 `MQTT`；YAML、XML、HTTP 不再作为已支持枚举暴露。
- 配置解析严格依据 `rawConfigFormat`，不通过首字符探测并容忍格式标识错误。
- Adapter 配置先按对应格式解析为规范化对象，再执行配置 schema 和业务引用完整性校验。
- 下发命令按参数 `dataType` 校验公开参数和 internal 注入值。
- 遥测按绑定属性的 `dataType` 校验后写入；不合法数据拒绝写入并记录上下文。
- MQTT 上行消息中的 `adapterName`、`devicePoint` 必须与 Topic 路径变量一致。

## 设备模型与约束

设备模型所有写入口汇入同一规范化、schema 校验和业务校验管线。删除或改造仍使用 `targetAttr`、`threshold`、`violationStateRef`、`GT/LT/GE/LE` 的旧约束接口和前端兼容逻辑，不保留旧设计兼容。

独立状态机写入口不能生成不满足当前设备模型 schema 的半成品；若保留接口，也必须调用与主保存链路相同的验证管线。

## 错误处理

- schema 错误在系统边界处返回具体路径和原因。
- 未支持动作、未知枚举和不合法数据类型均显式失败。
- MQTT 身份不一致和遥测类型不匹配不更新业务状态。
- 不以默认值或字符串后缀推断协议语义；需要默认策略时由集中初始化策略明确提供。

## 测试与验收

- 工作流：覆盖两分支/三分支聚合、未到达分支、重复消息、失败分支、子流程聚合。
- 状态机：覆盖 schema 动作与执行器一一对应、未知动作拒绝、信号 payload 校验。
- Adapter：覆盖格式严格选择、命令参数类型、internal 注入类型、遥测类型、Topic 与 payload 身份一致性。
- 设备模型：覆盖所有写入口均执行完整 schema 校验，旧约束字段被拒绝。
- 前端：覆盖元数据加载、无硬编码回退、设计器不生成未实现动作。
- 完成前运行后端测试、前端测试和生产构建；若环境问题阻断，必须报告实际命令和错误，不能声称通过。
