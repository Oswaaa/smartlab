# 流程模型到任务执行全链路优化设计

日期：2026-08-06  
状态：已确认总体架构，待规格复核

## 1. 目标

把当前割裂的工作流设计、任务创建、设备绑定、启动检查和运行反馈连成一条可用链路：

1. 用户在设计器中建立流程模型。
2. 后端根据同一模型完成校验、补全和编译。
3. 用户基于已发布的模型版本创建任务并绑定具体设备。
4. 系统在启动前完成模型、资源、设备状态机和适配器检查。
5. 执行期间，工作流、设备状态机和约束协同运行，并通过统一观察层反馈到原流程节点。

核心原则是“一个业务概念只有一个事实来源”。流程模型是唯一业务实体；执行定义是指定模型版本的派生编译结果，不是第二套可独立编辑的流程模型。

本设计取代旧工作流节点配置设计中让前端承担运行时契约拼装的部分。既有运行引擎和数据库结构可继续复用，但前后端职责重新划分。

## 2. 用户可见边界

### 2.1 用户可见并可配置

- 流程节点：开始、结束、设备能力、分支、汇聚、子流程。
- 设备模型与能力：流程设计阶段选择设备模型和能力，不选择具体设备实例。
- 接口：显示名称、方向、类型、允许信号及连接关系。
- 端口：显示名称、方向、数据类型、关联变量及数据连接。
- 变量：任务输入、节点内部变量、设备属性映射和节点输出。
- 业务触发条件与业务动作。
- 能力参数、分支条件和数据映射。

### 2.2 用户可见但不可修改

- 节点生命周期状态和转换。
- 系统启动、完成、失败动作。
- 节点模板要求的系统接口、系统端口和系统触发器的身份、方向与类型。

系统接口和系统端口仍显示在画布上，也允许参与连接；它们以锁定标识区分，用户不能删除或改变其系统语义。用户可以新增和编辑业务接口、业务端口、业务触发器和业务动作。

### 2.3 始终隐藏

- HTTP/API 地址和请求结构。
- 消息主题、协议报文和适配器调用细节。
- 内部数据库主键、运行时锁、调度器和消息关联实现。
- `resourceMap`、`bindingKey`、`nodeIdRef` 等内部传输或存储结构。

## 3. 总体架构

### 3.1 单一流程模型

流程模型版本保存以下业务事实：

- 节点及其稳定模型标识。
- 接口、端口、变量、业务触发器和业务动作。
- 执行连接和数据连接。
- 设备节点所需的设备模型、能力和参数。
- 子流程引用、分支条件及画布布局。

业务接口和业务端口只在流程模型中定义一次；必需的系统接口和系统端口只在全局节点模板中定义一次。编译器把两者合并成编辑和执行视图，前端编辑、后端校验、任务资源推导和运行观察都通过稳定标识引用它们，不复制出另一套接口或端口实体。

### 3.2 后端模型编译器

`WorkflowDefinitionCompiler` 从“只校验前端生成的完整运行时 JSON”调整为流程模型的唯一编译入口，负责：

1. 规范化用户提交的模型定义。
2. 按节点类型合并 `WorkflowNodeSystemContract` 中的系统生命周期、系统动作、系统接口和系统触发器。
3. 校验名称和稳定标识唯一性、接口方向和信号兼容性、端口数据类型、拓扑、子流程引用及设备模型能力。
4. 生成不可变的编译图，供发布检查和执行引擎使用。
5. 返回面向编辑器的规范化模型和面向用户的模型错误。

编译结果按“流程模型 ID + 版本”缓存或即时重建。缓存可以重复计算数据，但不形成可编辑业务实体，也不成为事实来源。

### 3.3 版本与状态

- `DRAFT`：允许保存尚未完整的模型，返回错误和警告，但不能创建新任务。
- `ACTIVE`：通过完整编译并发布的不可变版本，可用于创建任务。
- 修改已发布模型时创建新的草稿版本，不改变已有任务引用的版本。
- 任务必须记录准确的流程模型 ID 和版本，避免模型后来变化导致执行语义漂移。

## 4. 前端工作流设计器

### 4.1 页面结构

设计器保留三栏结构，但职责收敛：

- 左侧节点库：设备模型、子流程和功能节点。
- 中间画布：展示节点、接口、端口、执行连接和数据连接。
- 右侧属性面板：编辑所选节点或连接的业务定义。

节点属性面板分为：

1. **基础配置**：节点名称、设备模型能力、能力参数、子流程和分支条件。
2. **接口与端口**：显式显示系统项和业务项；系统项锁定，业务项可增删改。
3. **变量与数据映射**：变量类型、设备属性映射、端口关联和边数据映射。
4. **触发与动作**：业务项可配置，系统项只读。
5. **生命周期**：只读展示模板生成的状态和转换，不暴露 API 实现。

### 4.2 连接行为

- 接口连接表达执行或状态信号关系。
- 端口连接表达数据传递关系。
- 画布显示用户名称，不直接显示内部 handle ID。
- 建立连接时即时检查方向、类型、信号和数据类型兼容性。
- 设备节点到设备状态机的系统连接由模型编译器补全，但在设计器中以只读关系展示。
- 删除接口、端口或变量前检查引用，给出受影响连接，由用户确认业务删除；系统项禁止删除。

### 4.3 保存与发布

- “保存草稿”保存当前模型和画布布局，不要求立即可执行。
- “检查并发布”调用后端完整编译，错误直接定位到节点、接口、端口或连接。
- 前端不再生成或修复系统生命周期、系统动作和系统触发器。
- 后端返回规范化结果后，前端以返回值刷新模型，确保界面与事实来源一致。

## 5. 任务创建与资源绑定

### 5.1 任务创建流程

任务创建采用三个业务步骤：

1. 选择已发布的流程模型版本，填写任务名称和任务变量。
2. 根据后端返回的资源要求，为每个设备节点出现位置绑定具体设备实例。
3. 查看启动检查结果并创建任务。

界面不出现“资源映射”“设备路由”“状态机接口”等实现词汇，统一使用“设备绑定”和“启动检查”。

### 5.2 资源要求由后端推导

新增面向任务创建的资源要求查询能力。后端递归展开子流程，根据编译后的设备节点返回：

- 节点稳定标识和用户可读路径。
- 所属流程名称和节点名称。
- 所需设备模型、能力及必要状态。
- 可复用规则和已绑定状态。
- 兼容设备实例及不可用原因。

前端不再通过解析 `NODE_TO_DEVICE`、`DEVICE_TO_NODE` 或接口名称自行构造绑定路径。内部仍可使用资源映射存储，但它只由前端适配层和后端 DTO 转换，不暴露给用户。

### 5.3 启动检查

启动前检查以结构化结果一次返回：

- 模型版本仍处于可执行状态。
- 所有必需设备节点均已绑定。
- 绑定实例符合设备模型和能力要求。
- 设备实例生命周期、在线状态和状态机允许接收命令。
- 适配器连接可用。
- 任务约束引用有效。

检查失败时任务保持 `PENDING`，用户可在原页面修正绑定或变量，无需通过启动失败日志猜测原因。

## 6. 执行、约束与观察反馈

### 6.1 执行数据流

1. 任务启动后，执行引擎加载任务固定引用的编译版本。
2. 工作流引擎以模型节点稳定标识创建步骤并沿执行连接推进。
3. 设备节点使用“节点标识 + 设备实例标识 + 能力 + 参数 + 执行消息标识”向设备状态机发出命令。
4. 设备状态机使用同一执行消息标识回传完成、失败、状态和属性结果。
5. 工作流把结果写入模型定义的变量和输出端口，并激活后续节点。
6. 约束读取统一观察快照，在明确的检查点产生继续、告警、中止或能力限制结果。

### 6.2 观察层

统一观察层保存运行快照，不复制设备属性定义。属性定义仍来自设备模型；快照只记录“属性标识 + 值 + 时间 + 来源 + 质量”。

任务页面按流程模型节点展示：

- 当前节点及完成比例。
- 节点状态、开始时间、结束时间和耗时。
- 绑定设备及执行能力。
- 输入、输出和关键变量。
- 约束结果和失败原因。

消息 ID、协议报文和内部调用栈默认不展示，可保留在管理员诊断日志中。

## 7. 错误处理

错误按链路阶段统一建模：`DESIGN`、`PUBLISH`、`BINDING`、`PREFLIGHT`、`EXECUTION`。

每个错误至少包含：

- 稳定错误码。
- 用户可理解的说明。
- 关联的流程版本、节点、接口、端口或设备绑定标识。
- 是否阻塞当前操作。
- 可执行的修复建议。

处理规则：

- 草稿错误不阻止保存，但阻止发布。
- 发布错误必须定位回设计器元素。
- 绑定和启动检查错误必须定位到具体设备节点。
- 运行错误必须固化步骤状态和最后快照，不覆盖原始原因。
- 前端不得直接显示后端异常堆栈、JSON 路径或内部字段名。

## 8. 代码边界调整

### 8.1 前端

- 拆分体积过大的 `WorkflowDesigner.vue`，页面仅负责加载、选择和命令编排。
- 节点编辑逻辑分别收敛到接口端口、变量映射、触发动作和生命周期组件。
- `workflowNodeDefinition.js` 不再生成系统运行时契约，只保留编辑模型的纯函数和前端即时校验。
- `taskResourceBindings.js` 不再解释底层接口连接，改为消费后端资源要求 DTO。
- `TaskList.vue` 拆出任务创建、启动检查和运行详情组件。

### 8.2 后端

- `WorkflowDefinitionCompiler` 成为规范化、系统模板合并和完整编译的唯一入口。
- 工作流保存服务区分草稿保存和发布编译。
- 增加任务资源要求和启动检查的应用服务及 DTO。
- `WorkflowTaskResourceService` 使用稳定节点标识，不把节点名称当作唯一业务键。
- 执行步骤和观察快照记录流程版本、节点稳定标识及子流程出现路径。
- 现有工作流引擎、状态机命令端口、约束服务和观察注册表继续作为运行时边界，不在前端复制其规则。

## 9. 兼容与迁移

- 读取既有流程定义时，通过兼容适配器识别系统模板项和业务项，并生成稳定标识。
- 第一次保存旧模型时写回规范化定义；迁移前后接口、端口和连接语义保持不变。
- 对旧任务保留按原模型版本执行的能力，不把新草稿自动应用到运行中或历史任务。
- 迁移期间后端可接受旧保存结构，但立即转换成统一模型；新前端只发送新结构。
- 删除前端生成系统骨架的逻辑前，必须用兼容测试覆盖现有模型样本。

## 10. 测试策略

### 10.1 后端

- 编译器单元测试：系统模板合并、业务项保留、接口信号、端口类型、拓扑、子流程和设备能力。
- 保存与发布服务测试：不完整草稿可保存、非法模型不可发布、已发布版本不可变。
- 资源要求测试：主流程、重复子流程、多设备节点和稳定出现路径。
- 启动检查测试：缺少绑定、模型不匹配、设备离线、状态机忙、适配器不可用和约束无效。
- 执行集成测试：设备命令、状态反馈、端口数据传递、分支、约束中止和观察快照。
- 旧模型兼容测试：加载、规范化、保存和重新执行。

### 10.2 前端

- 纯函数测试：模型规范化、接口/端口连接校验、业务项编辑和系统项保护。
- 组件测试：节点属性面板、系统锁定项、发布错误定位、设备绑定和启动检查。
- 端到端测试：设计并发布模型、创建任务、绑定设备、启动、收到状态反馈并完成。
- 文案检查：普通任务用户界面不得出现 API、`resourceMap`、`bindingKey`、`NODE_TO_DEVICE` 等实现词汇。

## 11. 验收标准

1. 用户可以在画布上看见并连接接口和端口。
2. 用户可以配置变量、业务触发条件和业务动作；系统生命周期及系统动作保持只读。
3. 保存草稿后重新打开，所有业务模型元素和布局无损恢复。
4. 前端不再生成系统生命周期和系统动作，后端编译结果是唯一执行依据。
5. 只有完整发布的模型版本可以创建任务。
6. 任务绑定需求完全由后端根据模型版本推导，前端不解析状态机接口。
7. 用户可以完成“选择模型—绑定设备—启动检查—启动任务”，过程中不接触 API 或内部映射结构。
8. 设备状态机的完成或失败反馈能准确落回对应流程节点。
9. 约束结果和观察快照按同一流程版本、节点标识和设备实例关联。
10. 旧模型和旧任务在迁移后仍可读取，既有关键测试不回归。

## 12. 实施顺序

1. 固定新模型 DTO、稳定标识和编译器测试。
2. 后端实现规范化、模板合并、草稿保存和发布。
3. 改造设计器，使其只编辑模型并消费后端规范化结果。
4. 后端提供资源要求和启动检查，前端改造任务创建链路。
5. 补齐执行步骤稳定关联和观察反馈。
6. 完成旧模型迁移、全链路测试和用户文案清理。
