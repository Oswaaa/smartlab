# GetPLCData 重构修改方案

日期：2026-09-18  
状态：供评审的设计方案；尚未修改 adapter 实现，也未进行真机验收。

## 1. 结论与范围

建议保留 SmartLab 标准接入框架，重构 GetPLCData 的真实设备控制与仿真实现，补齐旧版设备能力。目标不是复刻旧 C++ 的全部代码，而是按新规范完整承接设备能力，修复旧、新两版已发现的错误。

本轮设计只针对 `adapter/new/GetPLCData`。MotionStageController、ValueAdapterMQTT 分别安排后续方案，不在本方案中一并改动。

依据：

- `Backend/src/main/resources/samples/adapter-development-guide.md`，尤其第 4、7.1、8、9、10 节。
- `Backend/src/main/resources/schemas/协议规范.json`：以实际消息信封为准。
- `Backend/src/main/resources/samples/adapterSetup.ini`、`adapter-config.schema.json` 和 `AdapterManifestService`：以现有配置格式及解析规则为准。
- `adapter/GetPLCData/GetPLCData/GetPLCData/PLCCtrl.cpp`、`PLCCtrl.h`：旧命令、寄存器及控制算法的代码依据。
- `fixture/adapter/反应釜/core.py` 及其路由、持久化测试：现有标准实现参考。指南中的 `fixture/adapter/reactor/core.py` 路径在当前工作区不存在，实际目录为“反应釜”。

## 2. 方案选择

比较三条路径：

1. **推荐：保留标准 core，重写设备层。** 保留 MQTT、注册、租约、分流和消息格式；在 Python 中重新实现通信、采集、闭环控制、命令状态和仿真。能够独立测试，也最符合规范对三模块的职责划分。
2. **仅修补现有 Python。** 可以消除死锁和解析错误，但仍需补齐外围设备、分段程序、压力闭环，最终仍会接近重构，容易残留“写完即成功”的逻辑。
3. **由 Python 包装旧 C++ 程序。** 短期可能复用驱动，但保留旧 TCP、数据库和线程模型的耦合；旧版也有反馈有效性、完成判定等问题，不能把它视为无缺陷的设备服务。

选择第 1 条。旧版保留作为比对依据和部署回退对象；切换时禁止新旧进程同时控制同一套 PLC/485 设备。

## 3. 不改变的规范边界

- 保留 `core.py`、`control.py`、`simulation.py`、`adapterSetup.ini`、`runtime.ini`、`requirements.txt`，`main.py` 继续只作为启动入口。
- 不新增 `northbound.py`，不另造 MQTT 主题、消息信封或 Setup 格式。
- `core` 不理解寄存器、PID、PLC 通道、设备报警阈值或仿真动力学。
- 真实 I/O 仅存在于 `control`；仿真仅处理虚拟点，不能调用真实驱动。
- 物理点来自 Setup；虚拟点通过 LEASE 派生并支持 RELEASE、重连、重启恢复。
- 控制与仿真上报相同的命令生命周期事件，并原样关联 `messageId`。
- 有效指令完成校验和接纳后，立即发出 `COMMAND_RUNNING`，实际 I/O 与等待均在后台执行。非法参数、未知点位和资源冲突可直接失败。
- 物理遥测使用 SINGLE；仿真运行中使用 BATCH，空闲时按规范允许的单点方式上报。
- 地址、密码、设备超时、PID 参数留在本地运行配置或设备驱动内，不进入注册原文。
- 给已有模板增加命令、属性和物理点属于填写既有契约，不需要改变 schema 或解析器结构。

`core` 原则上复用；如规范回归测试暴露通用缺陷，只做与规范一致的修复。例如持久化快照缺省值应是通用空状态，不能在 core 中为所有设备写死反应釜温压。不得因本次设备扩展而更改分流和租约语义，也不顺带修改其他两个 adapter。

## 4. 点位与设备能力组织

建议按下列组合设备边界设计，共 12 个物理点。这是基于旧代码通道结构提出的默认分组，不是已经完成的现场拓扑核验：

- **Reactor1～Reactor8**：保持现有名称及 ReactorUnitTemplate。每个反应通道包括反应温度、压力、对应冷体温度、两路气体流量，以及相关设定值和运行状态。
- **Incubator1、Incubator2**：两个保温箱，分别承载设温、读温、报警温度。
- **Chromatography1**：色谱温控单元，承载设温、读温、报警温度。
- **PLCSystem1**：共享 PLC 控制点，承载手自动开关、9 个使能位、报警静音、CO/H2 总阀。它代表真实共享控制器，不是虚拟点。

将冷体和两路流量归入同编号 Reactor，是为了让同一通道的控制和虚拟租约保持一致。如现场将它们作为独立可预约设备管理，再按同一规范拆成独立物理点；不同时暴露两套可以绕过彼此资源控制的重复入口。

Setup 在物理点中声明 `kind`、`index` 等固定标识，通过既有 `internal=true/sourceField` 机制注入。所有属性都有 attributeMapping。驱动启动时验证通道唯一性、范围和模板种类，不根据点名字面猜测硬件通道。

共享控制的特殊处理：

- 寄存器 267 的手自动模式是全局资源，不能伪装成 8 套互不影响的通道设置。
- 现有 Reactor 的 `setOperatingMode` 可以保留为兼容入口，但说明和回执必须标明影响整个 PLC；与 PLCSystem1 共用同一资源控制。
- 与正在执行的物理任务冲突的全局模式切换返回 BUSY，不悄悄改变其他通道的运行条件。
- 每个虚拟点独立持有仿真状态；虚拟共享控制只作用于该虚拟实例，不影响真机或其他租约。第一版不承诺跨多个虚拟租约的整套工厂联动仿真。

旧版的电机状态读取、停止、清报警、参数初始化属于驱动底层能力，分别纳入状态采集、停止压力调节及驱动维护接口。参数初始化不能在启动时盲目执行旧硬编码帧；只允许明确配置的调试流程触发。旧停止帧与其他电机帧格式存在疑点，必须核验地址、长度、CRC 和响应，不能直接复制或凭空补造。

旧版数据库直写、后端动态写表映射和 TCP `order=...` 服务不进入标准 adapter 主流程：数据统一通过规范 MQTT 遥测交给后端。上线验收必须证明原本需要保存的各类读数均能通过新链路入库。旧调用方仍依赖 TCP 时，应另立兼容网关需求；本次默认不保留第二条控制入口。

## 6. 真实控制层的内部设计

保持 `ControlImpl` 的标准接口不变。在 `control.py` 中按职责组织以下组件，暂不引入新的公共模块接口：

1. **Modbus TCP 传输器**：连接、按长度收包、完整响应校验、有限超时与重连。
2. **485 网关传输器**：RTU 帧组装、CRC 校验、设备地址校验、响应读取、电机状态与停止。
3. **寄存器映射**：集中保存地址、读写方向、数值类型、比例和范围；避免散落地址计算。
4. **采集快照**：保存实际读数、采集时间、有效性和连接状态；目标值与实测值完全分离。
5. **命令管理器**：校验、接纳、资源占用、执行状态、超时、取消、重复命令处理。
6. **温控程序和压力控制器**：推进各通道的长任务，依据反馈决定到位与完成。

### 6.1 通信与线程模型

- PLC 与 485 各有一个串行 I/O 执行器，同一连接最多一个在途事务；两个连接可以独立推进。
- 连接、关闭与事务执行在同一连接所有权下完成，不在普通 Lock 内再次调用加锁函数。
- PLC 先读完整 MBAP 头，再按其中长度收完 PDU；处理 TCP 分包、断流、异常响应、错误事务号、错误功能码和错误字节数。
- 0x06 写入必须核对返回地址和值，不能只检查“收到 12 字节”。有可读状态时增加对应读回确认。
- 485 需要明确区分“帧被确认”“电机运行状态”“压力已达到”，一次发送成功不等于加压完成。
- 短通信事务与长过程等待分离。采集、到位判断和 PID 更新使用短任务/状态机，不能在一个工作线程中 sleep 等到所有动作完成。
- 停止任务优先处理，在当前有界通信事务结束后先于普通任务执行；不能声称可抢断一个正在等待硬件响应的网络事务。
- 队列有容量限制，重连有退避和有限请求超时。过期任务失效后不得继续发出写操作。
- 丢失响应的脉冲命令执行结果可能不确定，不自动重发；先查询状态或使任务失败，避免一次加压变成两次。

### 6.2 寄存器与采集覆盖

以旧实现的地址为代码基线，并与现场 PLC 程序/点表核验：

- 反应温度：0～7，按旧逻辑有符号值 / 10。
- 压力：11 + 3 × (通道 - 1)，按旧逻辑有符号值 / 100。
- 十段反应程序：34 + 22 × (通道 - 1) + 2 × (段号 - 1)，后一个寄存器为分钟数。
- 冷体目标：54 + 22 × (通道 - 1)。
- 保温箱目标：210～211；反应报警：212～219；保温箱报警：224～225。
- 冷体报警：通道 1～4 为 220～223，5～8 分别为 289、290、292、291，不能误写成连续映射。
- 使能位：226～234；流量设定：235～250；流量反馈：251～266。
- 全局手自动：267；通道程序启动：268～275。
- 色谱反馈/报警/目标：276/277/278。
- 冷体反馈：279～286；保温箱反馈：287～288。
- 报警静音、CO、H2：293、294、295。

采集初版沿用旧版 0～296 的分块方式，单次最多 30 个寄存器，避免未经验证扩大设备请求规模。物理量按各自采集块记录真实采集时间，不将多次读取宣称为硬件原子快照；同一闭环所需数据要有一致的有效性与时间检查。

缺少有效反馈时：

- 不上报 25℃、0.1MPa 或目标值作为真实测量。
- 旧值可以留作内部诊断，但不能改成新时间戳持续冒充实时数据。
- 上报已声明的连接/数据无效状态或故障事件；ALIVE 心跳只代表 adapter 进程存活。
- 依赖反馈的任务不能成功结束；进入明确故障处理。

### 6.3 指令完成语义

每条命令只有一个最终结果，使用同一条命令的 `messageId`：

- **INSTANT**：确认设定或请求已被硬件接受，不表示物理量已经到位。
- **TARGET**：实测值进入配置容差，并满足连续样本/稳定时间条件；不能使用浮点数严格相等。
- **PROFILE**：按程序定义完成对应段的时间与反馈要求。PLC 的段计时从何时开始、何时结束必须以程序实际行为为准，不使用收到 MQTT 的时间简单代替。
- 写入失败、数据陈旧、反馈无效、设备异常分别报告可区分错误；到期为超时，不成功。
- 同一物理通道冲突的长任务返回 BUSY，不覆盖旧任务的目标和 messageId。不同通道可并行；同一通道温度与压力能否并行由显式资源集合决定，默认允许互不冲突的两类控制。
- 同一 `messageId`、点位、命令和参数的重投在进程内复用已有执行/终态，不重复写硬件；同 ID 不同内容直接失败。重启后不自动重放未完成的物理动作，也不承诺跨进程恰好执行一次。

现有命令兼容原则：

- 保留 `heat`、`pressurize`、`setOperatingMode`、`setAlarmTemp` 的名称和主要参数。
- `heat` 作为第一段快捷入口；新增 `setReactorStep` 显式提供段号、分钟数、完成策略和超时。`heat` 默认采用 TARGET 完成策略；设定的 PLC 段仍可继续运行，回执必须说明完成的是“到温”。
- `heat.durationSec` 进入真实 PLC 程序时必须能无损换算为支持的整分钟；无法表示的值返回参数错误，不再 `max(1, durationSec // 60)` 静默改变时长。仿真执行同样的参数可表示性校验，避免仿真通过、实机被拒绝。
- `pressurize.durationSec` 可作为仿真收敛时长输入；真实压力完成只由反馈判断，不能按该时长盲发脉冲或固定等待后成功。实际执行超时由独立的 `timeoutSec` / 本地默认配置控制。
- `holdTemperature` 保留“追加长时间保持段”的能力，段数满 10 时失败。旧代码使用 9999 分钟，这不是数学意义上的无限保持，契约描述必须准确。
- 不把旧版“写完即成功”当作需要兼容的正确行为。状态语义变化需要更新设备模型中的能力/事件映射并做工作流回归。

### 6.4 压力闭环

每通道维护目标、实测反馈时间、误差历史、积分、输出限幅、电机状态和当前任务。

- 只有压力反馈有效且足够新时计算控制输出。
- 保留按误差决定方向和电机动作的控制思想，重建明确采样周期、限幅、积分约束与到位判断。
- 旧代码参数 `kp=50`、`ki=0`、`kd=0.01` 作为现场校准的参考值，不声称换成不同采样周期后仍可原样使用。
- 正反向含义、电机速度单位、每转脉冲数及齿比以驱动/机械配置为准；禁止使用未经验证的 `目标MPa × 1000 = 脉冲数`。
- 到位后完成该次调节命令，并明确是否继续保持压力控制。建议默认保持当前设定值，直至新目标、停止或故障；完成命令不等于后台闭环消失。
- 反馈失效或电机故障时停止生成新的运动脉冲，并尝试经过验证的电机停止流程；停止无确认必须报告故障，不能报告设备已停止。
- 新增无参数 `stopPressure` 作为终止能力。其含义为停止压力调节/电机动作，不等于泄压，更不等于压力已归零。

旧代码中 `cllct_no_err` 被清零且本次检索未找到有效置位；到温判断使用零容差；一些返回码未传递给调用方。这些缺陷应修复而不是迁移。

### 6.5 停止、取消与重启

- `stopHeating`、`stopPressure` 使用独立指令 ID 和优先执行通道。
- 停止命令确认完成后，给停止命令发 COMPLETED，给被停止的原命令发 CANCELLED，分别使用各自的 messageId。
- 停止失败不发送假的 CANCELLED/COMPLETED；报告实际执行不确定性。
- 清理过期或被取消任务产生的待发送写操作，防止停止后旧任务再次写启动位。
- 重启先读取 PLC 程序和运行状态；不依据默认值假设所有设备处于停止。
- 分段程序的“下一段”与硬件状态无法可靠恢复时，拒绝自动追加并要求显式重新配置；不得从第 1 段覆盖运行中的程序。

## 7. 仿真层设计

保持标准 `SimulationImpl` 接口。使用同一 Setup 获取源物理点类型；在仿真构造时建立只读点位/模板索引，`attach` 按 physical_point 创建相应模型，不修改 core 的标准构造和 attach 接口。

- Reactor 模型包含反应温度、压力、冷体温度、两路流量及程序状态。
- Incubator、Chromatography、PLCSystem 分别有对应状态与命令处理。
- Registry 负责 attach/detach 幂等；每虚拟点拥有独立锁、时钟、活动命令和状态快照。
- 参数校验、命令名称和最终事件语义与真实层一致；不得复用真实层的通信等待或硬件超时。
- 推演使用虚拟步长推进；默认 `batchSize=20`、`intervalSec=0.5`、`simStepMs=1000`，校验规范边界。
- TARGET 在模型实际到位时结束；PROFILE 在对应虚拟程序条件满足时结束，不能仅因到温便跳过保温/程序阶段。
- 空闲每秒出数，虚拟时间保持单调且不继续按运行倍率飞升；不为贴近墙上时钟倒退已经生成的数据时间。
- 仿真曲线达到目标、发出目标事件与发出命令完成要由同一次状态推进决定，不能额外 sleep 假等待。
- 快照包含目标、实际量、程序段、模式、报警阈值等全部可恢复状态；运行任务若不能完整恢复，明确终结并保留物理量，不静默丢失任务或复位到默认值。
- RELEASE 取消该虚拟实例任务、阻止后续上报、清理资源，绝不影响物理点。

规范存在一处事件命名不一致：第 9.1 节提到 COMMAND_SUCCESS，而第 8、9.3、9.4 节和 Setup 示例使用 COMMAND_COMPLETED。本方案统一采用后者；如果维护指南，则单独修正文档笔误，不另引入一套成功事件。

## 9. 分阶段实施与验收

### 阶段一：契约与失败用例

- 固化本方案的 21 项能力映射、12 个点位建议及共享资源规则。
- 建立无网络、无真实设备的协议和驱动替身。
- 先复现首次连接死锁、正常响应解析失败、写失败仍成功、错误物理点、过期反馈完成等问题。
- 校验新的 INI 能被 AdapterManifestService 接受，每个属性有映射，每个声明的命令在真实/仿真两侧有处理。

交付：可追溯的能力清单和能发现现有故障的测试。

### 阶段二：通信与完整采集

- 重建 PLC/485 通信及连接所有权。
- 补齐全部采集、数值转换、有效性和超时处理。
- 测试 TCP 分片、断流、异常帧、错误 TID/CRC/设备地址、写回显不一致及重连。

交付：在协议替身上稳定通信，连接异常不死锁、不伪造遥测。

### 阶段三：所有设备命令与温控程序

- 实现寄存器设置、主动读取、使能、阀控制和报警阈值。
- 实现段配置、到温检测、程序完成、追加保持段、资源冲突与停止。
- 覆盖所有通道首尾地址、十段边界、冷体报警的不连续地址与分钟转换边界。

交付：21 类旧能力均有实现或明确的底层依赖；通信接受和物理完成不混淆。

### 阶段四：压力闭环与故障处理

- 实现有效反馈驱动的分通道控制、电机状态、停止及异常退出。
- 测试升压、降压、目标已满足、压力不变化、陈旧数据、电机报警、取消与并行温控。
- 对未确认的停止/驱动初始化协议保留明确失败路径，不用模拟成功掩盖。

交付：协议替身与可控物理模型上的闭环测试通过；真实控制参数仍需真机校准。

### 阶段五：多设备仿真与规范回归

- 仿真覆盖相同能力和不同模板；虚拟时钟和微批次参数可测试。
- 验证 LEASE 重复、RELEASE 重复、重启恢复、无租约内存的合法虚拟点恢复及物理/虚拟隔离。
- 对每种虚拟命令断言真实 I/O 调用次数为 0；对非法物理点同样断言 0。
- 验证事件 ID、唯一终态、声明与实际事件一致，防止只写契约不发事件。

交付：GetPLCData 在仿真模式下可完成系统流程，且标准 core 语义保持不变。

### 阶段六：系统与真机验收

- MQTT 注册、命令、事件、SINGLE/BATCH、租约全部按现有格式联调。
- 核对后端设备模型的新增能力与生命周期事件映射；逐项确认读数入库。
- 真机先只读核对全部点表，再逐通道测试写入、到位、程序计时、压力控制和停止。
- 现场核验温压量程、符号方向、速度单位、PLC 程序时间语义、电机停止与反馈协议。
- 停止旧进程后切换；失败时按部署记录回退，避免两套 adapter 同时写设备。

交付：分别出具软件回归结果和真实设备验收结果，不以仿真通过代替真机通过。
