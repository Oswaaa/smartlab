2. Related Work · 为什么现有方法还不够

现有方案各自解决一部分问题，却没有形成“任务级”的统一表达

脚本 / API 自动化

擅长接入设备和下发命令；但状态、数据流和安全边界往往散落在接口与代码中。

工作流编排

擅长描述步骤顺序与控制依赖；但一个节点通常仍是“动作”，没有携带设备状态与能力语义。

系统模型 / 数字孪生

擅长刻画设备资源与结构关系；但没有说明如何抽取任务所需能力并组织成可执行过程。

本工作的不同点：不把“设备调用、流程组织、系统描述”分开处理，而是以任务为单位，把能力、运行状态、数据依赖与约束组织成同一个可执行表示。
讲述重点：我们补上的不是某一个功能，而是“任务级语义”的缺口

3. Methodology · 总体方法

一个实验任务，是实验室系统在特定目标下的可执行切片

它从已有设备资源中选择能力，将这些能力按流程关系组织起来，并在整个过程中持续接受约束监督。

模型逻辑图：三层模型各司其职，协议为跨层交互提供统一语义

3.1 System Abstraction · 系统抽象

先把实验室看成一个持续演化的系统，再描述其中的一次任务

“执行实验”不只是依次发送指令；它还包含资源状态的变化、过程数据的传递，以及边界条件的持续维护。
R
资源层：长期存在

设备、能力、属性和状态机制是实验室的稳定基础。

F
工作流层：因任务而生

将与本次实验相关的设备能力组织成时序、控制和数据关系。

C
约束层：贯穿执行

持续观测资源与流程状态，在越界时触发相应处置。

P
协议规范：贯穿交互

让模型、运行时与设备适配器说同一种业务语言。

从系统整体到任务切片：这是后续建模与实现的共同坐标系

3.2 Static Resource Layer · 静态资源层

每台设备都要同时回答：“我会做什么”与“我正处于什么状态”

理论要点：能力描述不直接执行；状态机负责让执行具有可验证的过程语义
05 / 11
3.3 Dynamic Workflow Layer · 动态工作流层

工作流节点不是“命令包装器”，而是设备能力在任务中的过程映射

理论要点：一个节点同时拥有能力映射、生命周期、接口与数据上下文
06 / 11
3.4 Constraint Layer · 约束层

约束不是事后报警，而是在执行中持续守住允许的边界

理论要点：设备局部约束反应更快；任务约束拥有更完整的全局视角

4.2 Discussion · 讨论

实现的意义，是把“实验过程”从散落的代码逻辑中提升为可检查的模型

  • 可观察：任务为什么能执行、走到哪一步、何时进入异常，都能在模型与执行日志中定位。
  • 可配置：新任务优先复用已有设备模型、工作流片段和约束规则，而不是从头编写控制脚本。
  • 可演化：更换设备接口时，主要影响能力、协议或适配器；任务逻辑无需随设备细节一起重写。
  • 仍需验证：多设备协同、并发任务、长时间运行和更复杂异常分支，是下一阶段的系统性验证重点。
从原型到研究证据，下一步要回答的是：

同一套模型能否稳定覆盖更多真实实验任务，并且降低模型变更的影响范围？
讨论重点：当前案例证明“可实例化、可运行”；规模化与系统性指标验证仍待推进
