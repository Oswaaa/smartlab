02 · Central idea

核心观点：把实验室描述为一个可执行的任务系统

任务不是一串设备指令，而是对目标、资源、条件与过程的统一描述；模型负责表达，运行时负责兑现。

实验意图
可验证的模型
可观测的执行
由此，实验设计、设备协同、安全控制与过程追溯能够在同一语义框架下闭环。
不是“连设备”，而是“让任务在设备上可靠发生”
03 / 11
03 · Modeling framework

六类模型分别回答六个不可回避的问题

WHAT CAN IT DO

设备能力模型

设备提供哪些可调用能力、参数与资源？

WHAT STATE IS IT IN

设备状态机模型

设备何时可用、如何迁移、何时异常？

WHAT MUST HOLD

约束模型

哪些安全、工艺与资源条件必须始终成立？

HOW TO SPEAK

协议规范

业务语义如何转换为设备可理解的载荷？

WHAT TO DO NEXT

工作流模型

任务如何编排步骤、分支、等待与恢复？

HOW IT RUNS

系统执行规范

运行态如何记录、调度、监控和追溯？

框架的价值：用分工明确的模型覆盖实验执行的完整语义

06 · A task comes alive

一次实验任务，如何从“定义”走到“被看见的执行”

STEP 01

定义任务

选择目标、工作流与所需设备资源。

STEP 02

编译与校验

解析节点、参数与依赖，检查模型一致性。

STEP 03

调度动作

按流程调用动作，向适配器发出业务语义。

STEP 04

状态与约束

监听信号、推进状态、持续判定安全条件。

STEP 05

留存证据

记录执行日志、步骤结果与异常上下文。

关键变化：系统不再只“下命令”，而是能解释为什么能执行、执行到了哪里、何时应该停止。
示例闭环：任务定义 → 模型校验 → 动作执行 → 信号反馈 → 日志追溯

07 · Execution mechanism

“可执行”依赖于模型与运行时之间的契约

语义动作 · 示例表达
{
  "action": "setTemperature",
  "target": "reactor-01",
  "parameters": { "value": 80 },
  "preconditions": ["idle", "safe"]
}
1
工作流引擎解释任务

将节点编译为可执行动作，并维护步骤推进。

2
状态机确认设备语境

动作与反馈只在合法状态转换中发生。

3
约束引擎持续守护边界

将安全与工艺要求变成运行时可判定规则。

4
适配器兑现通信细节

把统一语义映射至 MQTT、PLC 或其他设备接口。

契约分离了“做什么”与“怎么发指令”，从而承受设备差异

08 · Project evidence

SmartLab 2.0 的工作重点：让框架从概念走向可运行的链路

MODEL MANAGEMENT

模型可配置

前端提供设备模型、设备实例、工作流、协议与约束等管理入口，让模型不只停留在代码内部。

RUNTIME ENGINE

模型可解释

后端实现工作流编译与执行、状态机事件处理、约束表达式求值与执行日志映射。

EDGE ADAPTER

模型可兑现

通过适配器清单、消息载荷映射及 MQTT / PLC 接入，连接统一任务语义与真实设备信号。

当前定位：已形成从建模、执行引擎到设备适配的纵向原型；后续验证将聚焦于具体实验任务的稳定性、可扩展性与可追溯性。
不把“系统页面”当贡献，而把贯通链路当验证框架的证据

09 · Research value

框架的研究价值，在于给智能实验室提供了共同的表达与执行语言

降低系统演化成本

设备变化时，优先调整能力、协议或适配器模型，而非重写整个任务逻辑。

提升过程可解释性

每一步都有模型依据、状态证据和约束语境，便于定位、复现与审计。

支持更高层自动化

一旦任务与能力被结构化表达，优化、推荐与智能规划才有可靠的操作对象。

下一阶段的核心问题不是“再接入多少设备”，而是：

能否用同一套模型稳定覆盖更多真实实验场景？
模型是系统工程与智能方法之间可复用的中间层
